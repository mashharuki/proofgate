## 1. 表紙（5秒）

ProofGate です。CDK の synth の時点で、権限昇格の道を止めるツールです。

## 2. 概要（削除。動画の25〜40秒が同じ内容）
以下は旧台本。使わない。

CDK アプリを synth すると、CloudFormation ができます。その直後に、ProofGate の関門を置きます。
経路がなければ通し、あれば止めます。

- 図の動き: 左から順に出て、関門の遮断棒が下り、通す・止めるの2本に分かれる。

## 3. 課題（11秒）

ここに3つの権限があります。ロールを渡せる、関数を作れる、S3 を読み書きできる。
どれも、1つずつ見ればふつうの権限です。
ところが、つなぐと、開発者のロールから Lambda を通って、保護したい S3 まで届きます。

- 図の動き: 上の3つの札にチェックが付き、下で矢印が順に伸びて S3 が赤くなる。

## 4. 既存ツールとの違い（12秒）

見出しは過去形「〜だった」。今回の1つのスタック、既定の設定で試した結果であることを示す。

cdk-nag、Checkov、Access Analyzer の指摘は、ポリシー単位です。丸で囲んだ、ここを指します。
ProofGate は、人から、ロール、S3 までを、つなげて経路として見ます。

- 図の動き: 3行は人のアイコンだけが琥珀色の枠で囲まれ、残りは薄い。最後の ProofGate の行で、矢印が4つを順につなぐ。
- 根拠（同じデモスタックを修正前と修正後で試した結果）:

| ツール | 修正前 | 修正後 | 記録 |
|---|---|---|---|
| cdk-nag 3.1.0（AwsSolutionsChecks） | ワイルドカードを3件指摘 | 2件 | `comparison/cdk-nag/`、`docs/submission/comparison.md` |
| Checkov 3.4.11 | `DeveloperRole` のポリシーに2件（CKV_AWS_110、CKV_AWS_111） | 同じ2件 | `comparison/checkov/` |
| Access Analyzer `validate-policy` | 0件 | 0件 | `comparison/access-analyzer/` |
| Access Analyzer `check-access-not-granted`（`iam:PassRole` を指定） | FAIL | PASS | 同上 |
| ProofGate 1.2.0 | 経路1件 | 0件 | `docs/submission/comparison.md` |

- 口頭で言えること: Access Analyzer は、禁止する権限を自分で指定すれば、`iam:PassRole` の有無は検出できる。ただし1つのポリシー文書だけを見るので、渡す先のロールが S3 に届くかどうかは判断しない。
- 言わないこと: 「ほかのツールは検出できない」。Checkov は設定次第で別の検査もできる。1つのスタック、既定の設定での結果である。

## 5. 道ができる条件（14秒）

道ができる条件は4つです。
ロールを渡せる。サービスを起動できる。そのロールがサービスに信頼されている。そして、保護したいバケットに届く。
全部そろったときだけ、権限昇格の経路ありとして止めます。ルール名は PG-IAM-004 です。

- 図の動き: 4枚の札が順に出て、最後に赤い帯「全部そろうと、権限昇格の経路あり」が出る。右端の PG-IAM-004 はルールID。
- 根拠: 起動アクションは879件（AWS Service Reference から生成）。

## 6. 2つの実装が食い違えば止める（13秒）

同じモデルを、TypeScript と Lean 4 が、別々に判定します。
Lean が検査するのは、TypeScript が出した4つの真偽値です。
2つが一致しなければ、どちらも信用せず、止めます。

- 図の動き: モデルから2本に分かれ、TypeScript と Lean がそれぞれ判定を出し、「一致？」で、一致は「そのまま」、食い違いは「止める」（PG-IAM-003）に進む。
- 正直な注意点: Lean が証明するのは、この有限のモデルの性質だけ。AWS の IAM 全体や、抽出処理の正しさを証明するものではない（`docs/ASSUMPTIONS.md`、`docs/PROOFS.md`）。「Lean が証明する」とは言わない。
- 根拠: TypeScript の評価器は、独立に書いた別のオラクルとの照合テストで、実際に不具合を見つけた（`docs/submission/kiro-usage.md`）。

## 7. 分からないものは通さない（11秒）

もうひとつ大事なのが、分からないものは通さないことです。
経路がなければ通す。経路があれば止める。読めない構文や、判定の食い違いも止めます。PG-IAM-003 です。

- 図の動き: テンプレートから3本の線が伸び、緑・赤・黄の札が順に出る。3つ目の札は「読めない」だけ（食い違いはスライド6が担当）。

## 8. 検証（11秒）

公開されている91の昇格経路で試しました。ロールを渡して新しく動かす形は47件中46件、全体では91件中60件を検出します。
見つけられなかった31件の内訳は、IAM ユーザーやグループの操作が11件、ほかのサービスの既存リソースの書き換えが16件、その他が4件です。どれも、今はまだ扱っていない形です。

- 図の動き: 棒が4本、左から順に伸び、最後に 60/91 が出る。
- 出典: Datadog の pathfinding.cloud（Apache-2.0）。内訳は `tests/data/pathfinding-cloud/results.json`。
- 根拠: 未検出31件の内訳を全件数えた（`tests/data/pathfinding-cloud/results.json`、`aws-paths.json`）。IAM ユーザー・グループ関連11件（経路名に User、Group、AccessKey、LoginProfile を含む。`iam:CreateAccessKey`、`iam:PutUserPolicy`、`iam:AddUserToGroup` など）。既存リソースの書き換え16件（分類 `existing-passrole`。`ssm:SendCommand`、`ecs:ExecuteCommand` など）。その他4件（`cloudformation-005`、`iam-001`、`iam-016`、`sts-001`）。
- 注意: 分類は経路名と分類名からの機械的な集計で、1件ずつの原因までは調べていない。「対象外のため」とは言い切らず、「今はまだ扱っていない形」と言う。今後の対応の約束はしない。

## デモ動画の台本（動画を正とする。約94秒、英語の字幕のみ）
