## 1. 表紙（5秒）

ProofGate です。CDK の synth の時点で、権限昇格の道を止めるツールです。

## 2. 概要（11秒）

CDK アプリを synth すると、CloudFormation ができます。その直後に、ProofGate の関門を置きます。
経路がなければ通し、あれば止めます。

- 図の動き: 左から順に出て、関門の遮断棒が下り、通す・止めるの2本に分かれる。

## 3. 課題1（11秒）

ここに3つの権限があります。ロールを渡せる、関数を作れる、S3 を読み書きできる。
どれも、1つずつ見ればふつうの権限です。
ところが、つなぐと、開発者のロールから Lambda を通って、保護したい S3 まで届きます。

- 図の動き: 上の3つの札にチェックが付き、下で矢印が順に伸びて S3 が赤くなる。

## 4. 課題2（11秒）

今のツールは、1文ずつ見ます。どの文も問題なしなので、見落とします。
欲しいのは、つなげて見て、「この主体はこのバケットに届く」と言うことです。

- 図の動き: 虫眼鏡が札を上から順に見ていく。右では4つがつながり、「経路が見える」が出る。
- 根拠: 同じスタックで cdk-nag は文ごとのワイルドカードを3件指摘し、ProofGate は経路1件を指摘した（`docs/submission/comparison.md`）。

## 5. 道ができる条件（14秒）

道ができる条件は4つです。
ロールを渡せる。サービスを起動できる。そのロールがサービスに信頼されている。そして、保護したいバケットに届く。
全部そろったときだけ、権限昇格の経路ありとして止めます。ルール名は PG-IAM-004 です。

- 図の動き: 4枚の札が順に出て、最後に赤い帯「全部そろうと、権限昇格の経路あり」が出る。右端の PG-IAM-004 はルールID。
- 根拠: 起動アクションは879件（AWS Service Reference から生成）。

## 6. アプローチ1（10秒）

流れは4段です。テンプレートを読み、小さなモデルにし、候補の経路を洗い出す。ここまでが TypeScript です。
最後の証明を、Lean 4 が行います。

- 図の動き: 4つのアイコンが順に出て、TypeScript と Lean 4 の括弧が付く。

## 7. アプローチ2（13秒）

Lean が見るのは、TypeScript が計算した4つの真偽値です。
4つとも true なら、AND の先が UNSAFE になります。
TypeScript と Lean の判定が食い違ったら、それも止めます。

- 図の動き: false の灰色が true の赤に変わり、AND を通って UNSAFE が出る。
- 正直な注意点: Lean が証明するのは、この有限のモデルの性質だけ。AWS の IAM 全体や、抽出処理の正しさを証明するものではない（`docs/ASSUMPTIONS.md`、`docs/PROOFS.md`）。

## 8. アプローチ3（11秒）

もうひとつ大事なのが、分からないものは通さないことです。
経路がなければ通す。経路があれば止める。読めない構文や、判定の食い違いも止めます。PG-IAM-003 です。

- 図の動き: テンプレートから3本の線が伸び、緑・赤・黄の札が順に出る。

## 9. 中扉（4秒）

さっそく止めてみます。

→ ここにデモ動画を挿入する。

## デモ動画の台本（別撮り、約60秒）

使うスタックは `examples/vulnerable-app`。AWS アカウントは要らない。

1. 通常の `cdk synth`。成功する（終了コード 0）。（約10秒）
2. ProofGate を有効にして `cdk synth`。止まる（終了コード 1）。画面の `PG-IAM-004` と、`DeveloperRole` が `ProtectedDataRole` を Lambda に渡して起動できる、という説明の行を見せる。（約20秒）
3. `iam:PassRole` の8行を消す（`fix.patch`）。（約10秒）
4. もう一度 ProofGate 付きで synth。今度は通る（終了コード 0）。（約10秒）
5. ひとこと: Lambda の広い権限はそのまま残っています。止めたのは、権限の広さではなく、経路です。（約10秒）

`pnpm demo:fix` で4手順を一度に確認できる。撮影前に Node.js 26 以上と `elan` を用意する（`nvm use`）。

## 10. まとめ（12秒）

879の起動アクションを検査し、既知の昇格経路は91件中60件を検出します。
Kiro では、7つの spec、steering、hook、MCP で作りました。
SCP や権限境界、ロールの連鎖は、まだ対象外です。次は、ロール連鎖とデータ境界に進みます。

- 根拠: 60/91 は pathfinding.cloud のベンチマーク（`tests/pathfinding-benchmark.test.ts`）。Kiro の内容は `docs/submission/kiro-usage.md`。
- 注意: Kiro を導入する前の作業を、Kiro でやったこととして話さない（`.kiro/steering/kiroween.md` の方針）。

## 補足スライド（ルールID一覧、動画には入れない）

動画の本編には含めず、質問されたときや、提出資料に付けるための1枚。

- PG-IAM-003: ProofGate が読めない構文や、TypeScript と Lean の判定の食い違い。安全扱いにせず止める。
- PG-IAM-004: 保護したい S3 に届く権限昇格の経路。ロールを渡して起動する形と、すでに動いている関数などを書き換える形がある。
- PG-IAM-005: ロールが自分で IAM を書き換えられる構成。自分のロールへの権限付与など。

意図して許可したい場合は、設定の `allowedPassRoleTargets`（004 の対象ロール）と `allowedPolicyWriters`（005 の書き込み役）に書く。
