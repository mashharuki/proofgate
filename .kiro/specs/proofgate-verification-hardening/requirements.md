# Requirements: proofgate-verification-hardening

Status: APPROVED (revision 3). `design.md` (revision 3) and `tasks.md` are approved. Implementation is in progress; the task boxes in `tasks.md` show the current state.

## Introduction

ProofGate decides whether a CloudFormation stack contains the privilege-escalation path `PG-IAM-004`. Two components decide: the TypeScript evaluator (`evaluate` in `@proofgate/core`) and a Lean theorem generated by `generateLean`. If they disagree, `ProofGateValidator` fails closed with `PG-IAM-003`.

Current tests use hand-written fixtures in `tests/proofgate.test.ts`. This spec adds generated tests in two separate layers.

### Test layers

| Layer               | Input generated                             | Checked code                     | Expected answer comes from                                                                |
| ------------------- | ------------------------------------------- | -------------------------------- | ----------------------------------------------------------------------------------------- |
| Model-level PBT     | `StackModel` and `ProofGateConfig` directly | `evaluate`, `generateLean`, Lean | The oracle, built from the construction recipe                                            |
| Extractor-level PBT | CloudFormation template fragments           | `extractStack`                   | The construction recipe of the fragment (expected model, or expected unsupported finding) |

The layers have separate generators, separate reports, and separate counts. A failure in one layer is never reported as a failure of the other.

### Responsibility of each comparison

| Comparison                        | What it verifies                                                                                                              |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Oracle vs TypeScript (`evaluate`) | The semantics of the IAM model interpretation: matching, trust, PassRole resolution, and Lambda control.                      |
| TypeScript vs Lean                | That the candidate facts produced by `generateLean` and the Lean logic agree. Lean receives four Booleans per candidate path. |
| Recipe vs `extractStack`          | That the CloudFormation-to-model conversion keeps what it should and rejects what it cannot model.                            |

Lean does not independently verify the CloudFormation template or the IAM statements. No document, test name, report, or Kiro write-up produced by this spec may say or imply that it does (Requirement 14).

### Findings from reading the code that shape these requirements

1. **The Lean side does not see IAM statements.** `generateLean` serializes four Booleans per candidate path (`canPassRole`, `canControlLambda`, `targetIsLambdaAssumable`, `targetCanAccess`), and Lean only evaluates their conjunction. All wildcard matching, trust checking, and PassRole resolution happen in TypeScript.
2. **A TypeScript-versus-Lean comparison alone is therefore weak.** It would catch a bug in the generator or the Lean AND, but not a wrong wildcard match, because both sides receive the same wrong Booleans.
3. **Using `evaluate` as the expected answer would be circular.** The test needs an expected verdict that does not come from `evaluate`.

These findings are why Requirements 2 and 3 exist.

## Glossary

- **Case**: one generated `StackModel` together with one `ProofGateConfig`.
- **Oracle verdict**: the expected safe or unsafe verdict, derived from how the case was constructed, not from running `evaluate` or Lean.
- **TS verdict**: safe if `evaluate` returns no violations, otherwise unsafe.
- **Lean verdict**: the result of checking the module from `generateLean` with the pinned Lean toolchain.
- **Candidate facts**: the four Booleans per candidate path that `generateLean` serializes for Lean.
- **Counterexample**: a case where any two of the oracle verdict, TS verdict, and Lean verdict differ. In the extractor layer: a fragment where `extractStack` differs from the construction recipe.
- **Valid StackModel**: a `StackModel` of version `"1"` that satisfies the preconditions the extractor enforces before proof generation (at least one role and at least one supported Statement) together with a `ProofGateConfig` that has at least one non-empty protected bucket ARN.

## Requirements

### Requirement 1: Generate safe, unsafe, and boundary models (Model-level PBT)

**User story:** As a ProofGate maintainer, I want automatically generated IAM models of known safety, so that I can test combinations I would not write by hand.

#### Acceptance criteria

1. WHEN the generator is run with a seed, THE generator SHALL produce Cases deterministically from that seed.
2. THE generator SHALL produce Cases that are unsafe by construction: each has a principal role, a target role, a protected bucket, and all four `PG-IAM-004` conditions satisfied.
3. THE generator SHALL produce Cases that are safe by construction: each is derived from an unsafe Case by removing or breaking exactly one of the four conditions.
4. THE generator SHALL vary these dimensions, within the limits supported by the extractor and evaluator:
   - number of roles and number of statements per role
   - `*` wildcards in Action and Resource patterns, including `iam:*`, `lambda:*`, `s3:*`, and ARN-embedded wildcards
   - Lambda control through `lambda:CreateFunction` alone, through `UpdateFunctionConfiguration` plus `UpdateFunctionCode`, and through only one of the two
   - trust principals: `lambda.amazonaws.com`, `*`, and other services
   - PassRole targets by Logical ID, by role name, and by ARN with differing partition and account parts
   - protected bucket ARNs with and without a trailing slash, and with several buckets
   - object-level ARN (`bucket/*`) versus bucket-level ARN
   - case differences in Action names
   - `allowedPassRoleTargets` set and unset
5. THE generator SHALL include explicit boundary Cases: a single role, principal equal to target, no protected-bucket access, and statements split across several statements that only together form the path.
6. THE Model-level generator SHALL produce `StackModel` values directly, without going through CloudFormation, and SHALL NOT produce Cases that the extractor would reject as unsupported. Rejection is tested in the extractor layer (Requirement 12).

### Requirement 2: Independent oracle

**User story:** As a reviewer, I want the expected verdict to come from somewhere other than the code under test, so that the test cannot pass just because the evaluator is wrong in the same way as the check.

#### Acceptance criteria

1. THE oracle verdict SHALL be derived from the construction recipe of each Case (which conditions were established or broken), and SHALL NOT call `evaluate`, `generateLean`, or Lean.
2. WHERE a matching rule is needed to decide the oracle verdict, THE test code SHALL use an independent implementation that does not import the production matcher.
3. WHEN the oracle verdict differs from the TS verdict, THE test SHALL fail and report a Counterexample.
4. THE test suite SHALL include metamorphic properties that need no expected answer, at least:
   - adding a statement that is irrelevant to PG-IAM-004 does not change the verdict
   - reordering roles or statements does not change the verdict
   - adding an Allow statement never turns an unsafe Case into a safe one
5. THE test suite SHALL document, in English, what the oracle does not cover (for example Explicit Deny, which `evaluate` currently ignores, and which is conservative).

### Requirement 3: TypeScript and Lean agreement

**User story:** As a maintainer, I want proof that the Lean check and the TypeScript evaluator agree for every generated Case, so that the fail-closed disagreement path is exercised rather than assumed.

#### Acceptance criteria

1. FOR every Case in the Lean-checked set (Requirement 8.4), THE test SHALL compare the TS verdict and the Lean verdict.
2. THE Lean verdict SHALL be taken only from the explicit `PROOFGATE_SAFE` and `PROOFGATE_UNSAFE` markers, using the same decision rule as `ProofGateValidator`.
3. IF the Lean process fails to start, times out, or prints neither marker, THEN THE test SHALL fail with an infrastructure error. It SHALL NOT count that Case as safe, unsafe, or skipped.
4. THE test SHALL also check the oracle verdict against the Lean verdict, so that all three agree.
5. THE test SHALL cover the generated Lean for models with zero candidate paths and with many candidate paths.
6. THE TS-versus-Lean comparison SHALL be described, in code comments and reports, as a check of candidate facts against the Lean logic, as defined in Requirement 14.

### Requirement 4: Bounded Lean process launches

**User story:** As a CI maintainer, I want test time that does not grow with every generated case, so that the suite stays practical.

#### Acceptance criteria

1. IN the generated agreement profile (the Model-level run that compares oracle, TypeScript, and Lean), THE number of Lean verification process launches SHALL be at most 2 per run.
2. THE following SHALL NOT count toward that limit: the one-time Lake build of the Lean project, the existing fixed integration tests, and the harness self-check (Requirement 6.3). `design.md` SHALL state how many launches the self-check uses.
3. THE number of launches SHALL NOT increase when the number of Cases increases. A larger profile (Requirement 8.3) SHALL be handled by larger batches, not by more launches, or the design SHALL state the batch size limit and the resulting launch count explicitly.
4. THE batching method SHALL still attribute a verdict to each individual Case. A batch verdict alone SHALL NOT be accepted.
5. THE batching SHALL NOT weaken the production code path. `ProofGateValidator` behavior SHALL be unchanged.
6. THE test SHALL reuse the already built Lean project and SHALL NOT rebuild it per Case.
7. THE extractor layer (Requirement 12) SHALL NOT launch Lean.

### Requirement 5: Reproducibility and minimal counterexamples

**User story:** As a developer who sees a failure, I want to rerun the exact failing case and see the smallest version, so that I can fix the bug quickly.

#### Acceptance criteria

1. THE default seed SHALL be fixed in the repository, so that CI runs are deterministic.
2. WHERE the environment variable for the seed is set, THE tests SHALL use that seed, which allows wider exploratory runs without changing code.
3. WHEN a Counterexample is found, THE test output SHALL include the seed, the case index, and the Case as JSON that can be pasted into a test.
4. WHEN a Counterexample is found, THE test SHALL reduce it to a smaller failing Case (fewer roles, statements, or actions) before reporting, and SHALL report the reduced Case.
5. EACH shrinking step SHALL keep the candidate a Valid StackModel. A reduction that produces an invalid model SHALL be rejected, not repaired silently.
6. EACH shrinking step SHALL keep the original disagreement: the same pair of verdicts that differed in the original Counterexample SHALL still differ.
7. BEFORE reporting, THE harness SHALL rerun the oracle, the TypeScript evaluator, and Lean on the final reduced Case and SHALL confirm the disagreement from those fresh results. A reduced Case whose disagreement cannot be reproduced SHALL NOT be reported as the minimal case. In that situation the harness SHALL report the last confirmed Case instead.
8. IF the oracle cannot produce a verdict for a reduced model, THEN THE shrinking step SHALL be rejected.
9. Lean reruns during shrinking happen only after a failure. They are outside the limit in Requirement 4.1, SHALL be batched per shrinking round, and SHALL be bounded by a maximum number of rounds documented in `design.md`.
10. FOR the extractor layer, THE same rules apply with "valid CloudFormation fragment" in place of Valid StackModel and `extractStack` compared with the recipe in place of the three verdicts.
11. THE test suite SHALL include a regression mechanism so that a reported Counterexample can be added as a fixed test.

### Requirement 6: Fail-closed behavior stays covered

**User story:** As a security reviewer, I want generated tests to confirm that unknown input is rejected, so that new coverage does not drift toward accepting more.

#### Acceptance criteria

1. THE extractor-level generated tests (Requirement 12) SHALL cover unsupported syntax (`Condition`, `NotAction`, `NotResource`, non-literal values, managed policies, unknown IAM resource types) and SHALL assert that the extractor reports each as unsupported and returns no model.
2. THE test suite SHALL assert that an empty `protectedBucketArns` is rejected.
3. THE test suite SHALL include a self-check showing the harness itself detects faults: with a deliberately wrong evaluator or a deliberately wrong Lean module supplied only inside the test, the harness SHALL report a Counterexample.
4. No change in this spec SHALL make `ProofGateValidator` accept a template that it rejects with `PG-IAM-003` today. Verdict changes for `PG-IAM-004` follow Requirement 7.7.

### Requirement 7: Existing behavior is preserved

**User story:** As a user of ProofGate, I want the published behavior to remain the same.

#### Acceptance criteria

1. WHEN `pnpm synth` runs, THE result SHALL be that both `safe-app` and `vulnerable-app` succeed.
2. WHEN `pnpm verify:demo` runs, THE result SHALL be that `safe-app` succeeds and `vulnerable-app` exits with code 1 and `PG-IAM-004`.
3. THE existing test cases and their assertions SHALL continue to pass.
4. THE spec SHALL NOT delete, skip, or weaken any existing test or assertion without explicit user approval. Adding new tests is allowed.
5. IF a Counterexample reveals a defect in production code, THEN THE defect SHALL be fixed within this spec, as a task of its own that contains the minimal fix and a regression test built from the reduced Counterexample.
6. A fix SHALL NOT make ProofGate accept anything that it rejects with `PG-IAM-003` today.
7. IF a fix changes a `PG-IAM-004` verdict from unsafe to safe, THEN THE change SHALL be justified by the oracle and reported to the user before it is merged into the task list as done.

### Requirement 8: CI practicality

**User story:** As a maintainer, I want the new tests to run in the existing CI job within a reasonable time.

#### Acceptance criteria

1. THE default test profile SHALL run inside `pnpm test` and the existing GitHub Actions job without a new workflow, unless `design.md` justifies one.
2. THE added time for the default profile SHALL be at most 60 seconds locally and at most 3 minutes in CI. These limits are confirmed by the user.
3. WHERE a larger profile is selected (more Cases, other seeds), THE project SHALL provide a documented way to run it manually, separate from the default profile.
4. THE default Model-level profile SHALL generate at least 2,000 Cases for the TypeScript and oracle comparison. The extractor layer has its own count, documented in `design.md`. IF the measured Lean batch time cannot fit the limits in 8.2 at that size, THEN `design.md` SHALL state the largest Lean-checked subset that fits, and the remaining Cases SHALL still be checked against the oracle. The Lean-checked subset SHALL include every boundary Case and a seeded sample of the rest.
5. THE CI run SHALL print the seed and the Case counts (generated, safe, unsafe, boundary) so that coverage is visible.

### Requirement 9: Package and dependency boundaries

**User story:** As an npm consumer, I want published packages to contain no test-only code and no new runtime dependencies.

#### Acceptance criteria

1. THE generator, oracle, and harness code SHALL live outside the published `files` of every package (under `tests/` or an unpublished location).
2. `pnpm pack:check` SHALL continue to pass, and tarballs SHALL NOT contain test-only code.
3. THE spec SHALL add no `dependencies` or `peerDependencies` to any published package.
4. WHERE a test library such as fast-check is considered, THE design SHALL compare it with a small in-repo seeded generator. The user has allowed fast-check as an exact-pinned `devDependency` to be evaluated; adding it still requires the design to justify the choice. The comparison SHALL cover lockfile impact, Knip and jscpd behavior, shrinking quality, and maintenance cost.
5. THE spec SHALL keep Node.js 26 or later, pnpm 11, TypeScript strict mode, and the Lean toolchain pinned in `lean-toolchain` unchanged.
6. THE spec SHALL NOT make Kiro a runtime or build dependency of any package.

### Requirement 10: Code quality and conventions

#### Acceptance criteria

1. `pnpm quality`, `pnpm typecheck`, `pnpm test`, and `pnpm pack:check` SHALL pass.
2. New source comments SHALL follow the existing Japanese comment policy. Spec documents under `.kiro` SHALL be in English.
3. THE spec SHALL NOT edit generated output (`dist/`, `cdk.out/`, `.lake/`).

### Requirement 11: Auditable Kiro work record

**User story:** As a hackathon judge, I want to see how Kiro was used to build this feature, without overstated claims.

#### Acceptance criteria

1. EACH Kiro session working on this spec SHALL add a dated row to the usage log in `.kiro/steering/kiroween.md`, naming the Kiro app, the feature used (spec, steering, PBT, hooks, MCP), and the concrete result.
2. THE record SHALL include failures, rejected design options, and Counterexamples found, not only successes.
3. THE record SHALL NOT include work that was not done in Kiro, and SHALL NOT contain credentials, tokens, or credit codes.
4. WHERE Kiro's property-based testing or correctness features are used, THE record SHALL state which requirements they were used for and what they found. IF they are not used, THE record SHALL say so and give the reason.

### Requirement 12: Extractor-level PBT

**User story:** As a maintainer, I want generated CloudFormation fragments checked against `extractStack`, so that the template-to-model step is tested as thoroughly as the model-level logic.

#### Acceptance criteria

1. THE extractor-layer generator SHALL produce CloudFormation template fragments deterministically from a seed (Requirement 5.1 and 5.2 apply).
2. FOR supported fragments, THE test SHALL compare `extractStack` output with the expected model recorded in the construction recipe: role Logical IDs, role names, trust services, and each Statement's effect, actions, resources, and `sourcePath`.
3. THE supported fragments SHALL vary at least: Action and Resource given as a string or as an array, inline `Policies` on a role, `AWS::IAM::Policy` attached through `Ref`, several roles, several Statements, and Allow and Deny effects.
4. FOR unsupported fragments, THE test SHALL assert that `extractStack` returns at least one unsupported finding whose `sourcePath` points into the offending part of the fragment, and returns no model.
5. THE unsupported fragments SHALL cover the constructs listed in `docs/SUPPORTED_IAM.md`, including `Condition`, `NotAction`, `NotResource`, non-literal values, managed policies, non-default role paths, unsupported IAM resource types, and malformed Policy Documents.
6. FOR fragments that mix supported and unsupported parts, THE test SHALL assert that no model is returned (an unsupported part SHALL NOT be dropped silently).
7. WHERE a fragment has no roles or no supported Statements, THE test SHALL assert rejection.
8. THE extractor layer MAY pass a successfully extracted model to the Model-level checks, but its failures SHALL be reported under the extractor layer, with the fragment as JSON.

### Requirement 13: Oracle rules verified against official AWS information

**User story:** As a reviewer, I want the oracle's IAM matching rules to be confirmed from AWS's official documentation, so that the oracle is not just a second copy of an unchecked assumption.

#### Acceptance criteria

1. BEFORE the oracle is implemented, `design.md` SHALL record, for each item below, what the official AWS documentation says, the source URL, and the decision taken for the oracle:
   - case sensitivity of IAM Action names
   - case sensitivity of Resource ARNs
   - wildcard semantics (`*` and `?`, and where wildcards may appear)
   - `iam:PassRole` Resource matching
   - S3 bucket ARN versus object ARN
   - the Lambda service trust principal
   - `allowedPassRoleTargets`
2. `allowedPassRoleTargets` is a ProofGate configuration option and not an AWS feature. FOR that item, THE design SHALL document the intended behavior from the existing code and README instead of AWS documentation, and SHALL state that distinction.
3. WHERE the AWS Documentation MCP server or the AWS IaC MCP server is used, THE design SHALL record which one, which pages were read, and the conclusion drawn. The same note SHALL be added to the Kiro usage log (Requirement 11).
4. WHERE the official documentation is silent, ambiguous, or disagrees with the current behavior of `evaluate`, THE design SHALL list the item as an open decision for the user. It SHALL NOT silently choose a rule. The current evaluator matches Action and Resource patterns case-insensitively. Whether that is correct for each is to be checked, and over-matching, which is conservative, SHALL be distinguished from under-matching, which is not.
5. THE oracle code SHALL reference the recorded decision for each rule in an English comment.

### Requirement 14: Honest statement of what each check proves

**User story:** As a judge or a user, I want accurate claims about what the tests and the Lean check establish.

#### Acceptance criteria

1. THE test code, reports, and documents produced by this spec SHALL state that Oracle versus TypeScript verifies the semantics of the IAM model interpretation.
2. THEY SHALL state that TypeScript versus Lean verifies agreement between the generated candidate facts and the Lean logic.
3. THEY SHALL NOT state or imply that Lean independently verifies the CloudFormation template, the IAM Statements as a whole, the extractor, the generator, or AWS IAM behavior.
4. THE oracle's coverage limits SHALL be listed in English (Requirement 2.5).
5. THE Kiro write-up and the usage log SHALL use the same wording.

## Out of scope

- Adding new IAM rules or new supported syntax.
  - Exception: the corrections D1 and D5 below are in scope as defect fixes under Requirements 7.5 to 7.7.
- Proving the extractor or the generator correct in Lean.
- Modeling Explicit Deny, SCPs, permissions boundaries, or conditions.
- Deploying to AWS.
- Changing `ProofGateValidator` to batch Lean calls in production.

## Decisions recorded

1. Time limits: 60 seconds locally, 3 minutes in CI. Confirmed.
2. Default run size: thousands of Cases (Requirement 8.4). Lean-checked size is bounded by measured time.
3. `fast-check` may be evaluated in `design.md` as an exact-pinned devDependency.
4. Defects found are fixed within this spec (Requirement 7.5 to 7.7).

## Scope clarification (design review)

The design review decided that two corrections found by the oracle and probes are **in scope** as defect fixes under Requirements 7.5 to 7.7. They are not new rules or new syntax.

- **D1: S3 access by intersection.** A target role that can access any object in a protected bucket, including a prefix-scoped Resource such as `bucket/reports/*`, counts as access to the protected bucket. The Resource is compared with the protected bucket's object set by intersection. This adds `PG-IAM-004` findings.
- **D5: IAM policy variables are unsupported.** A Statement Resource string that contains IAM policy variable syntax (for example `${aws:username}`) is reported as unsupported with `PG-IAM-003`, with no partial model. Variables are not evaluated. This rejects more input (Fail Closed) and never accepts more.

The `?` single-character wildcard fix in the evaluator is also a defect fix under Requirement 7.5. The design is in `design.md` section 13. Neither correction may make ProofGate accept anything it rejects with `PG-IAM-003` today (Requirement 7.6).
